# 个人作品集：GitHub Pages + Supabase

前端保留深蓝与金色、手机适配、分类筛选、图片大图。后端使用 Supabase 的 PostgreSQL、Auth 和 Storage。网站的「管理作品」支持管理员登录、新增与编辑作品、自定义分类、图片自动压缩、移入回收站和恢复。访客只能浏览。

## 多页作品 / 作品文件夹（2026-11-26）

在 Supabase SQL Editor 新建查询，执行 `backend/migrations/20261126_albums.sql` 全部内容。本脚本基于已完成的分类/回收站升级；可重复执行，不删除图片或重置页面顺序。全新项目运行完整 `backend/schema.sql` 即可。

- 一件作品可包含 1–30 张图，首页显示封面和页数；点击卡片查看，支持上一页/下一页、缩略图、键盘左右键和手机左右滑动。
- 在管理面板选择作品，「添加作品页面」可多选图片，也可分批追加。每张图片仍使用 50 MiB 原图上限和自动压缩流程。
- 可以给页面命名为「正面」「背面」等，调整顺序、设为封面或移除单页。**第一张就是封面**，所有调整点击「保存修改」才生效。
- 旧的单图作品自动保留为第一页。静态图片路径也会保留；如果原来的占位图片尚不存在，可在编辑列表中移除该占位页，再添加真实图片。
- 移除单页不物理删除云端文件；整件作品移入回收站/恢复时，全部页面一起处理。当前没有单页回收站；未保存时可放弃编辑重新打开，已保存后需要重新添加移除的页。
- 图片会逐张压缩、逐张上传，所有图片上传完成后，页面路径、顺序和名称通过一次数据库写入一起保存。中途失败不会更新一半的页面列表；会尝试清理本次新上传的文件，已发布内页受存储权限保护。
- `projects.images` 保存有序 JSON 数组，每项为 `{path, caption}` 或 `{static_image, caption}`。数据库验证页数、名称长度、路径及重复图片，并自动同步旧的封面字段，兼容尚未刷新的旧客户端。
- 旧数据库仍能展示原来的单图作品；新版保存前会检查是否升级，未升级会明确提示并在上传前停止。

验收：选一个节目单，追加背面 → 命名正面/背面 → 保存 → 访客打开并翻页 → 设置背面为封面 → 保存刷新 → 移除一页 → 保存 → 删除整件作品再从回收站恢复，核对剩余页面和顺序。浏览器视觉、手机手势和实际云端上传仍需在升级后验证。

## 现有项目升级（2026-11-26）

在 Supabase SQL Editor 执行 `backend/migrations/20261126_gallery.sql`。它会添加 `deleted_at` 字段、把固定分类改为 1–30 字符的自定义分类，并让访客只能读取未删除的作品，管理员仍可读取回收站。脚本可重复执行，不删除任何作品或图片。新安装执行下面完整 `schema.sql` 即可。

升级前首页会兼容旧表，继续读取已有作品；自定义分类和回收站需要升级后才能使用。无需修改 Auth、公钥或存储桶限额。

新版采用深蓝封面、暖白作品区，支持按分类和关键词查找。图片完整展示，点击可放大。移动端为单列布局，管理面板和大图均支持 Escape 关闭及原生对话框焦点管理。

### 使用新功能

- 新增/编辑：在分类输入框选择已有分类，或直接输入新分类。发布后会自动生成首页筛选项。分类来自实际作品，最后一件作品移走后，该分类不再显示在首页。
- 删除：在管理面板「选择操作」中选中作品，点击「删除作品」，确认移入回收站。也可从首页卡片的「编辑作品」进入。
- 恢复：在管理面板的「回收站」中点击「恢复」。恢复保留原图和作品信息。
- 删除是软删除：只从公共列表中移除，图片仍占用空间，已知的公开图片直链仍可访问。没有提供永久删除功能。
- 压缩：支持最大 50 MiB 的 JPG、PNG、WebP 原图，浏览器自动优化到最长边不超过 3200 像素并尽量控制在 2 MiB；必要时降低质量和尺寸，最终必须低于云端 8 MiB 限额。小图不反复压缩，原始电脑文件不会被改动。
- 压缩会显示原始/处理后大小及尺寸。请检查预览再发布，密集文字海报可先裁切为细节图。超大尺寸图片可能受手机内存影响；HEIC、PDF、PPT 需先导出为支持的图片格式。

### 升级验收

1. 执行升级 SQL 后，访客仍能看到原有作品；未登录无法读取回收站或更新记录。
2. 管理员新增一个自定义分类，发布后分类筛选和搜索都能找到作品。
3. 选择一张超过 10 MiB 的真实图片，核对优化大小和预览，发布后在另一设备检查清晰度。
4. 删除一件测试作品，确认匿名访客列表不再显示它；从回收站恢复后重新出现。
5. 编辑时不选新图，应保留原图；取消删除不能改变作品。

## 首次部署

### 1. 创建 Supabase 项目

在 https://supabase.com/dashboard 创建项目，选择你和主要访客访问较好的区域。数据库密码自行保管，不要提交到 GitHub。项目创建后，在 SQL Editor 粘贴并执行 `backend/schema.sql` 的全部内容。此脚本会：

- 建立管理员白名单和作品表，并启用 RLS 权限规则。
- 建立公开图片桶 `portfolio`，限制 JPG、PNG、WebP，单文件最大 8 MiB。
- 预填原有六个作品，保留 `images/` 路径作为未补图时的回退。

脚本可以重复执行，不覆盖已经修改的六个作品。请使用独立的新项目，避免与其他应用的宽松权限策略叠加。

### 2. 创建唯一管理员

在 Authentication 的 Users 页面创建你的邮箱密码用户（如有自动确认邮箱选项，开启）。没有提供网页注册入口；同时在 Authentication 的登录/注册设置中关闭新用户注册。

复制该用户的 UUID，在 SQL Editor 执行以下 SQL，把示例 UUID 替换为真实值：

```sql
insert into public.portfolio_admins (user_id)
values ('这里替换为管理员用户的UUID')
on conflict do nothing;
```

只有白名单中的用户可以添加或编辑作品、上传图片。普通登录用户也没有写权限。移除白名单会立即撤销后续写入权限。

### 3. 连接前端

从项目的 Connect / API Keys 页面取得项目 URL 和 **publishable key**（或旧的 anon key），填写 `config.js`：

```js
export const backendConfig = {
  url: 'https://你的项目ID.supabase.co',
  publicKey: '你的publishable或anon公钥'
};
```

这两个值是供浏览器使用的公开配置，可以提交到公开仓库。**不能填 secret key、service_role key、数据库密码或管理员密码**。公钥不是管理员凭证；实际权限由登录身份和 RLS 决定。

前端没有自动保存登录信息；关闭/刷新页面后需重新登录。登录期间的短期令牌和续期令牌只存在内存中。

### 4. 发布

```sh
git add index.html app.js album.js image-processing.js config.js backend-client.js backend package.json package-lock.json .gitignore tests README.md
git commit -m "feat: add Supabase artwork management"
git push origin main
```

原 GitHub Pages 设置继续使用 main / root。部署完成后打开 https://olmanseide212-star.github.io/portfolio/ ，在底部点击「管理作品」，输入你的管理员邮箱和密码。

新增作品：选择「新增作品」，填写标题、分类、介绍，选图片并点击「发布作品」。

补充原作品：在「操作」下拉框选择原有作品，选图片并发布。已有图片的作品如果不选新图，会保留原图。

## 验收清单（连接真实项目后执行）

1. 未登录打开网站：看到六个作品，可筛选、适配手机。
2. 使用错误密码：登录失败，不能上传。
3. 使用普通非管理员账号：拒绝管理；直接调用 REST 写入也应被 RLS 拒绝。
4. 管理员给一张占位卡上传图片：发布成功后标题、介绍和图片展示正常，大图可打开。
5. 用另一台设备或隐身窗口打开首页：无需登录能看到刚发布的图片。
6. 新增一个作品，确认刷新后仍然存在；编辑时不选图片，确认原图不变。
7. 大于 10 MiB 的 JPG/PNG/WebP 自动压缩；大于 50 MiB 的源文件和 SVG 被拒绝；压缩/发布期间表单禁用，避免并发提交。
8. 退出或刷新后，必须重新登录才能管理。
9. 临时让后端不可达：首页显示静态回退和加载失败提示，不伪装为最新在线数据。

## 本地运行与测试

需要 Node.js 20+、Python 3。网站运行时无 npm 依赖、无构建步骤；测试用 PGlite 在本地运行 PostgreSQL：

```sh
npm ci
npm test
npm run preview
```

访问 http://localhost:8000 ，不要双击 HTML 使用 file://（ES modules 需要 HTTP）。HTTP 和图片编码测试使用模拟响应；SQL 测试在隔离的本地 PostgreSQL（PGlite）中执行真实迁移，验证数据兼容、封面同步、访问权限和内页文件保护。测试不会连接或修改云端数据。真实浏览器图片解码/编码、Supabase Storage API 和跨设备验收仍需按上面的清单执行。

## 工程设计

浏览器 → Supabase Auth（验证身份）→ 带 JWT 的 Storage 上传 → projects 写入 → 公开首页读取作品。

- 作品表只存文字、图片路径和排序信息；图片二进制存在 Storage。没有 base64 图片写入 localStorage 的问题。
- `portfolio_admins` 由数据库管理员维护；浏览器没有修改白名单的权限。作品表和图片桶分别实施权限检查，隐藏上传按钮不是安全措施。
- 图片使用用户 UUID / 随机 UUID 命名，避免中文路径兼容问题和同名覆盖。图片桶是公开的，只适合展示用图片，不适合敏感文件。
- 图片先上传、作品后写入；数据库写入失败会尝试删除未引用的图片。Storage 删除策略禁止删除正在被作品引用的图，避免响应丢失后误删已发布图片。
- 图片与数据库不共享一个事务，网络中断仍可能留下孤立文件。更换图片也暂时保留旧图，便于人工恢复；长期使用可增加服务端定时清理。请在 Supabase Storage 中谨慎清理已确认不再引用的文件。
- 标题和描述使用 `textContent` 渲染，不把用户输入拼成 HTML。图片类型和大小既在客户端限制，也由云端桶配置限制。未做图片重新编码或内容审核，上传权限只给可信管理员。
- 后端加载失败保留原静态卡片；后端正常返回空表则显示空状态。没有实时订阅，新访客和刷新页面会获取最新作品。
- 不需要常驻自建服务器，但仍需要维护 Supabase 账号、用量、存储和备份。数据库与图片应分别备份；服务套餐/配额以项目控制台当前信息为准。
